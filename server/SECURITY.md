# 安全验收清单（上线前必查）

> 本文档是「音辩卫士」接入云服务后、正式上线前的**安全验收 check 项**。
> 核心结论先行：**「表隔离」和「文件隔离」是两层，必须各自成立，缺一不可。**
> 数据库 RLS 做得再严，只要 Storage 文件没有同等级别的访问控制，
> 就等于把最敏感的产出（检测结论图）暴露了。

---

## 一、风险定性（为什么这张清单存在）

### 已知最严重漏洞：Storage 文件访问控制

`publishableKey` 是公开的，任何人都可以绕过前端直接调 Storage API。若平台策略未配好，后果：

| 漏洞 | 攻击路径 | 后果 |
|---|---|---|
| **读穿（隐私泄露）** | 任何登录用户按路径读别人的报告图；路径含时间戳/原文件名可猜，或允许 listing 直接枚举 | 泄露他人检测结论（报告图本身就是结果） |
| **写穿（篡改/删除）** | 任何登录用户覆盖/删除别人的文件 | 篡改报告图，伪造「AI/真人」结论 |
| **匿名读穿（更糟）** | Storage 默认允许匿名访问 | 连登录都不用，公开 URL 直接读图 |

**定性**：这是**必须在正式上线前关闭**的高优先级安全项，不是「以后再说」。

---

## 二、三道防线（缺一不可）

### 防线 1 —— 平台侧：Storage 按 uid 分桶 + 访问控制（最根本）

这是**唯一能挡住「绕过前端直连 API」的层**。

- [ ] Storage 路径强制按用户分桶：
  - `users/<uid>/...` → 仅 `uid` 本人可读写删
  - `shared/<uid>/...` → `uid` 本人可写删，其他登录用户只读
- [ ] 分桶访问控制由**平台在服务端强制**，而非前端自觉
- [ ] **匿名访问必须关闭**（无登录不得读写任何对象）

> ⚠️ 这是决定生死的一层，必须实测验证，不能「文档说支持」就默认安全。

### 防线 2 —— 前端：换签名 URL 前校验 path 前缀（辅助）

已在 `lib/cloud-reports.ts` 的 `reportImageUrl()` 实现：

```ts
const allowedPrefixes = [`shared/${user.id}/`, `users/${user.id}/`];
const owned = allowedPrefixes.some((p) => path.startsWith(p));
if (!owned) throw new Error("无权访问该报告图片");
```

- [ ] 确认所有「对象路径 → 签名 URL」的调用点都经过此校验

> 局限：这只防「自己的前端误操作」，**挡不住攻击者绕过前端直连 Storage API**。
> 它是补充，不是主防线。

### 防线 3 —— 数据层：路径不可猜 + 禁 listing（加固）

- [ ] 路径用 `crypto.randomUUID()` 生成，**禁用**「原文件名 + 时间戳」等可预测组合
- [ ] **禁止 listing**（不给任何「列出目录下文件」的权限），堵死枚举
- [ ] 路径不携带任何用户可识别信息（昵称、文件名、uid 明文）

## 三、上线前验收清单（逐项实测）

### A. 文件隔离（Storage）

| # | 验收项 | 通过标准 |
|---|---|---|
| A1 | 匿名访问 | 未登录，直接打对象 URL → 必须 401/403，读不到任何图 |
| A2 | 跨用户读 | 用户 A 读 `users/B/...` 或 `shared/B/...` → 必须拒绝 |
| A3 | 跨用户写 | 用户 A 覆盖/删除 B 的文件 → 必须拒绝 |
| A4 | listing | 任何用户尝试列出 `shared/` 下他人文件 → 必须拒绝/空 |
| A5 | 本人正常读写 | A 读写 `users/A/...` → 正常 |

### B. 表隔离（数据库 RLS）

| # | 验收项 | 通过标准 |
|---|---|---|
| B1 | 跨用户读 | A 查 reports 表 → 只返回自己的行 |
| B2 | 跨用户写 | A 插入 `owner_id = B` 的行 → 被 `DEFAULT auth.uid()` + RLS 拒绝 |
| B3 | 跨用户删 | A 删 B 的报告 → 返回空数组，数据不动 |
| B4 | 数据约束 | 写入 `risk_level = "banana"`、`ai_probability = 500` → 数据库拒绝 |

### C. 密钥与日志

| # | 验收项 | 通过标准 |
|---|---|---|
| C1 | 前端只放公开配置 | 代码里只有 `endpoint` + `publishableKey`，无长期密钥 |
| C2 | 敏感信息不打码不上屏 | token、手机号、邮箱、文件 URL 不进日志/回复 |
| C3 | 签名 URL 短期有效 | 默认 600 秒，不长期持久化 |

---

## 四、若 Storage 隔离不达标，降级方案

如果平台 Storage 的「按 uid 强制分桶」达不到上述标准，**禁止把含敏感结论的报告图走 Storage 公开链路**。改用：

1. **服务端签名 + 严格鉴权**：图不落 Storage，走自己的后端签名下发；
2. **或「不长期存图」**：只存报告元数据，图片「每次现生成、现下载」，不落盘。

> 结论：在 Storage 隔离实测通过之前，**不要上传含敏感结论的报告图**。
